etch
Precise file mutations, automatic commits.
Built for agents working against git repos.

The home directory pattern

A new kind of repository is emerging: the agent home directory. Not a codebase that ships to production, but a git-backed knowledge store where agents and humans collaborate on structured data. Think:

  • Personal knowledge bases — daily logs, notes, and dossiers in markdown with rich frontmatter
  • Task trackers — markdown files where status: complete or [snoozed:: 2026-05-10] are real, queryable data
  • People/CRM directories — a folder of markdown files, one per person, with structured metadata and append-only interaction logs
  • Config-as-data repos — YAML and JSON files that represent system state, not just system configuration
  • Wiki-style collaboration — multiple agents and humans editing overlapping files, always committing, always rolling forward

In these repos, git isn't version control for code—it's the database engine. Commits aren't milestones; they're the transaction log. Every small mutation should be its own commit, because git history is the audit trail. The filesystem conventions—frontmatter fields, inline tags like [due:: 2026-03-01], section headers as stable anchors—form a lightweight schema that agents navigate constantly.

A single agent session might mark a task complete, add a snooze date to an action item, update a person's contact info, and append to a daily log—each one its own auditable commit. This is the always commit, always roll forward workflow.

Why patches are the wrong tool

Today, agents do these mechanical edits through general-purpose patch tools: construct a diff, apply it, hope the whitespace is right, stage the file, write a commit message. Each of those steps burns tokens and introduces failure modes. Hallucinated diffs. Off-by-one line numbers. Trailing newline mismatches. And the stakes are higher than they look—when your filesystem is your database, a botched edit corrupts your data.

The edits themselves are boringly predictable: set this frontmatter field, delete that YAML key, replace this markdown section, append to that list. For structured, mechanical mutations on known formats, a diff is the wrong level of abstraction. You wouldn't use sed to set a JSON key. So why use a patch to update a frontmatter tag?

You want to reserve patches and diffs for the cases that actually need them—novel edits to code, prose rewriting, complex refactors. The mechanical stuff should be a solved problem.

What etch is

etch is a small CLI for mechanical mutations to text and data files. It knows about a fixed set of file formats—Markdown, JSON, YAML, CSV—and a fixed set of operations on them. Every successful mutating call becomes a git commit by default.

The scope is intentionally narrow. No network. No subprocesses. No Turing-complete scripting. Just precise structural edits that land as atomic commits.

  • FormatsMarkdown (with frontmatter), JSON, YAML, CSV—inferred from file extension
  • Operationsset, delete, append, add, remove on structured paths; replace-section on markdown headings; create, move, copy, delete on files; table operations on CSV and markdown tables; guards (exists, missing, contains)
  • OutputA git commit with touched paths materialized by default
  • LanguageGo, single binary, using git as the transaction backend

Install

go install github.com/brandonbloom/etch/cmd/etch@latest

Requires Go 1.25.3+ and Git.

See it work

Pick a scenario to see what etch does:

terminal
# Mark a task as complete in a markdown file
$ etch set tasks/onboarding.md frontmatter.status "complete"
 
[main a1f9c3e] etch set tasks/onboarding.md frontmatter.status
1 file changed, 1 insertion(+), 1 deletion(-)

One command. The frontmatter field is updated and the result is committed. No patch construction, no staging, no commit message to write.

terminal
# Snooze an action item and update its tracking metadata
$ etch run - <<'SCRIPT'
set tasks/review-proposal.md frontmatter.snooze "2026-05-10"
set tasks/review-proposal.md frontmatter.status "deferred"
append people/alice.md frontmatter.tags '"pending-review"'
replace-section log/2026-04-27.md "## Activity" <<EOF
- Deferred proposal review to May 10
- Added pending-review tag to Alice's dossier
EOF
SCRIPT
 
[main b7e4d12] etch: 4 changes across 3 files
3 files changed, 6 insertions(+), 2 deletions(-)

All four operations land as a single atomic commit. If any one fails, none of them are applied. Each line in the script is the same syntax you'd use on the command line directly.

The plan is a structured JSON description of exactly what would change. It's produced by the same code path as real execution, stopped one step before side effects. A host runtime can present this to a human for approval and cache that approval by plan hash. For human review and mechanical replay, --dry-run lowers the plan to a git am-compatible mailbox patch.

Three design principles

1. Commits are the contract

A successful mutating etch call produces a git commit unless every operation is an idempotent no-op. That's the whole point. Read operations never commit.

2. CLI and script syntax are identical

A line in an etch script is the same tokens you'd type at the shell. Agents can prototype interactively and paste commands into scripts without translation.

# These are equivalent:
$ etch set config.json settings.theme "dark"

$ echo 'set config.json settings.theme "dark"' | etch run -

3. No escape hatches

The script syntax has no variables, no expansions, no subshells, no pipes. $FOO is literally the four characters $, F, O, O. Composition happens at the shell level, outside etch. This is what keeps etch's own blast radius statically bounded.

Parse. The input (CLI args or script lines) is tokenized using shell quoting rules. No expansion of any kind—what you wrote is what the operations receive. Heredocs are resolved at this stage.

Concurrency: optimistic STM

Multiple agents (or humans) can work on the same repo simultaneously. etch handles this using the same approach as software transactional memory:

two agents, one repo
# Two agents working on the same knowledge base
 
A$ etch set people/alice.md frontmatter.last_contact "2026-04-27"
B$ etch set tasks/review.md frontmatter.status "complete"
 
# Different files → both succeed, two commits
# Same file → one wins, the other re-plans and retries

Each invocation reads its input files from the committed state at HEAD and builds its commit in an isolated temporary index—it never uses your staging area as transaction state, and unrelated dirty files are ignored. After the commit lands, etch materializes only the touched paths into your working tree by default. On conflict, etch automatically re-reads the latest HEAD and retries (up to --retries, default 3). The caller never sees the retry unless the budget is exhausted.

HEAD, not the working tree. etch always reads from the committed state at HEAD, not from dirty checkout files. This means local edits to a file don't affect etch's input—only committed content matters. Consistency is enforced by a compare-and-swap on the branch ref at commit time: if another writer moved HEAD since planning began, the transaction restarts.

Why etch can be safe to allow

The goal: a user can grant permission for etch on a repo without that grant becoming equivalent to "always allow shell." Exact blanket allow-list guidance depends on the host agent's permission model.

🚫
No network
etch makes zero network calls. No HTTP, no DNS, no sockets. Data stays local.
🔒
No process spawning
etch does not exec anything except git, and only for the specific operations it needs (read refs, write objects, update refs).
📁
No filesystem escape
Reads and writes stay under CWD, not the repo root. Paths are relative, cannot contain .. or .git segments, and cannot escape through symlinks.
🛡️
No DSL escape hatch
No variables, no expansion, no subshells. The blast radius is statically bounded by the script text.

For an additional layer, a host runtime can use plan hashing as an authorization primitive:

# Step 1: compute and inspect the plan
plan=$(etch --plan set tasks/review.md frontmatter.status "complete")

# Step 2: present to user, get approval, cache the plan hash

# Step 3: future host integrations can execute only if the plan still matches

If anything changed after approval—file contents, branch state, even etch's own behavior across a version upgrade—the recomputed hash changes. The execution pin is an integration feature, not required for the standalone CLI.
