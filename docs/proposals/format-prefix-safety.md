# Format Prefix Safety

## Summary

Validate the final bytes of format-explicit plumbing commands when the target
path advertises a different Etch-supported structured format by extension.

This addresses the adopter report that `etch yaml set test.json b --json 2`
can parse a JSON file as YAML and then write YAML-shaped output back to a
`.json` path. Documentation explains why explicit prefixes select their own
parser and writer, but Etch should not commit bytes that are invalid according
to the format Etch itself would infer for the path.

## Candidate Commands

```sh
etch yaml set state.json b --json 2
etch jsonl append events.json '{"kind":"prompt"}'
etch json set state.yaml b --json 2
```

The first command fails if the final bytes are not valid JSON. The second
command fails once appending a JSONL record would leave `events.json` invalid
as JSON. The third command can succeed because JSON output is valid YAML.

## Semantics

- Porcelain commands keep inferring the parser and writer from the path.
- Format-explicit plumbing prefixes keep selecting the parser and writer.
- After planning the final transaction bytes, Etch validates the output when a
  format-explicit command writes a path whose extension maps to a different
  Etch-supported structured format.
- The validation target is the inferred format, not the explicit command
  format.
- Unknown or extensionless paths remain allowed; Etch does not content-sniff to
  guess a better format.
- Mismatches can succeed when the generated bytes are valid in the inferred
  format. For example, JSON bytes are valid YAML.
- Mismatches fail before commit, ref update, or checkout materialization when
  the final bytes are invalid in the inferred format.
- The first implementation covers whole-file structured prefixes: JSON, YAML,
  and JSONL/NDJSON. Part-specific Markdown commands can adopt the same rule if
  they gain risky cross-format behavior.

## Rationale

Format-explicit commands are valuable for scripts and unusual extensions, but
the common typo is destructive when the command succeeds, commits, and leaves a
path whose extension tells downstream tools to parse it differently from the
bytes Etch wrote.

Rejecting every extension mismatch is too blunt. Many repositories use
extensionless files or custom extensions for JSON and YAML, and JSON is also a
valid subset of YAML. The useful safety rule is narrower: if Etch knows what a
path claims to be, Etch should not make the path unreadable as that format.

## Impact

Spec:

- Define inferred-output validation for format-explicit commands.
- Define which inferred formats are validated.
- Define mismatch failures as runtime failures because the command shape is
  valid but the planned output is unsafe for the advertised path.

Docs:

- Update `help formats` with the inferred-output validation rule.
- Add examples showing porcelain inference versus explicit plumbing.

Code:

- Track explicit format/path mismatches during planning.
- Validate final transaction bytes for changed paths before computing the
  planned tree.
- Add tests for YAML output to `.json`, JSON output to `.yaml`, JSONL output to
  `.json`, unknown extensions, and extensionless files.
- Add tests proving no file content changes or commits occur on invalid
  inferred output.

## Open Questions

- Should CSV output validation join this rule, given CSV's broad validity?
- Should part-specific Markdown plumbing such as `frontmatter` and `md section`
  be included immediately or handled separately?
- How should future TOML and JSONC support extend the inferred-format map?
