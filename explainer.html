etch
Precise file mutations, automatic commits.
Built for agents working against git repos.
Status: etch is under active development and not yet released. This page describes the design intent. Specific verb names, flags, and behaviors may change before the first release.

Git as a database

Something interesting is happening with AI agents: they're getting home directories. Not just scratch space—persistent, git-backed repositories where the filesystem is the database. Markdown files with YAML frontmatter as records. JSON and YAML for config and state. CSV for tabular data. Wiki-links and inline metadata tags connecting it all together. Git commits as the transaction log.

In these environments, agents aren't writing code that ships to production—they're maintaining living knowledge bases, personal CRMs, task trackers, daily logs, and structured notes. The workflow is always commit, always roll forward. A single agent session might mark a task complete, add a snooze date to an action item, update a person's contact info, and append to a daily log—all as separate, auditable commits.

Why patches are the wrong tool

Today, agents do these mechanical edits through general-purpose patch tools: construct a diff, apply it, hope the whitespace is right, stage the file, write a commit message. Each of those steps burns tokens and introduces failure modes. Hallucinated diffs. Off-by-one line numbers. Trailing newline mismatches. And the stakes are higher than they look—when your filesystem is your database, a botched edit corrupts your data.

The edits themselves are boringly predictable: set this frontmatter field, delete that YAML key, replace this markdown section, append to that list. For structured, mechanical mutations on known formats, a diff is the wrong level of abstraction. You wouldn't use sed to set a JSON key. So why use a patch to update a frontmatter tag?

You want to reserve patches and diffs for the cases that actually need them—novel edits to code, prose rewriting, complex refactors. The mechanical stuff should be a solved problem.

What etch is

etch is a small CLI for mechanical mutations to text and data files. It knows about a fixed set of file formats—Markdown, JSON, YAML—and a fixed set of operations on them. Every successful mutating call becomes a git commit by default.

The scope is intentionally narrow. No network. No subprocesses. No Turing-complete scripting. Just precise structural edits that land as atomic commits.

  • FormatsMarkdown (with frontmatter), JSON, YAML—inferred from file extension
  • OperationsSet, delete, append, replace on structured paths and sections
  • OutputA git commit (by default) or working-tree change (with --no-commit)
  • LanguageGo, single static binary, no runtime dependencies

See it work

Pick a scenario to see what etch does:

terminal
# Mark a task as complete in a markdown file
$ etch set tasks/onboarding.md frontmatter.status "complete"
 
[main a1f9c3e] etch: set frontmatter.status in tasks/onboarding.md
1 file changed, 1 insertion(+), 1 deletion(-)

One command. The frontmatter field is updated and the result is committed. No patch construction, no staging, no commit message to write.

terminal
# Snooze an action item and update its tracking metadata
$ etch tx <<'SCRIPT'
set tasks/review-proposal.md frontmatter.snooze "2026-05-10"
set tasks/review-proposal.md frontmatter.status "deferred"
append people/alice.md frontmatter.tags '"pending-review"'
replace-section log/2026-04-27.md "## Activity" <<EOF
- Deferred proposal review to May 10
- Added pending-review tag to Alice's dossier
EOF
SCRIPT
 
[main b7e4d12] etch: 4 changes across 3 files
3 files changed, 6 insertions(+), 2 deletions(-)

All four operations land as a single atomic commit. If any one fails, none of them are applied. Each line in the script is the same syntax you'd use on the command line directly.

terminal
# Preview what would happen, without writing anything
$ etch --plan set tasks/review.md frontmatter.status "complete"

The plan is a structured JSON description of exactly what would change. It's produced by the same code path as real execution, stopped one step before writing. A host runtime can present this to a human for approval, hash it, and then execute only if the same plan would result.

Three design principles

1. Commits are the default

A successful mutating etch call produces a git commit. That's the whole point. You opt out with --no-commit, not in. Read operations never commit.

2. CLI and script syntax are identical

A line in an etch script is the same tokens you'd type at the shell. Agents can prototype interactively and paste commands into scripts without translation.

# These are equivalent:
$ etch set config.json settings.theme "dark"

$ echo 'set config.json settings.theme "dark"' | etch tx -

3. No escape hatches

The script syntax has no variables, no expansions, no subshells, no pipes. $FOO is literally the four characters $, F, O, O. Composition happens at the shell level, outside etch. This is what makes "always allow etch" a defensible authorization stance.

Parse. The input (CLI args or script lines) is tokenized using shell quoting rules. No expansion of any kind—what you wrote is what the operations receive. Heredocs are resolved at this stage.

Concurrency: optimistic STM

Multiple agents (or humans) can work on the same repo simultaneously. etch handles this using the same approach as software transactional memory:

two agents, one repo
# Two agents working on the same knowledge base
 
A$ etch set people/alice.md frontmatter.last_contact "2026-04-27"
B$ etch set tasks/review.md frontmatter.status "complete"
 
# Different files → both succeed, two commits
# Same file → one wins, the other re-plans and retries

Each invocation works in an isolated temporary index—it never touches your staging area or unrelated dirty files. On conflict, etch automatically re-reads the current state and retries (up to --retries, default 3). The caller never sees the retry unless the budget is exhausted.

Two checks, not one. etch validates that the files it read haven't changed on disk (read-set validation) and that the branch ref hasn't moved (ref CAS). Both are necessary: dirty working-tree edits don't move refs, and concurrent commits don't touch the working tree.

Why "always allow etch" is safe

The goal: a user can grant blanket permission for etch on a repo without that grant becoming equivalent to "always allow shell."

🚫
No network
etch makes zero network calls. No HTTP, no DNS, no sockets. Data stays local.
🔒
No process spawning
etch does not exec anything except git, and only for the specific operations it needs (read refs, write objects, update refs).
📁
No filesystem escape
Reads and writes stay within the git repo root. No symlink chasing past the boundary.
🛡️
No DSL escape hatch
No variables, no expansion, no subshells. The blast radius is statically bounded by the script text.

For an additional layer, a host runtime can use plan hashing as an authorization primitive:

# Step 1: compute and inspect the plan
plan=$(etch --plan set tasks/review.md frontmatter.status "complete")

# Step 2: present to user, get approval, extract hash

# Step 3: execute only if the plan hasn't changed
etch --require-plan-hash abc123 set tasks/review.md frontmatter.status "complete"

If anything changed between planning and execution—file contents, branch state, even etch's own behavior across a version upgrade—the hash won't match and etch refuses to run.

The home directory pattern

A new kind of repository is emerging: the agent home directory. Not a codebase that ships to production, but a git-backed knowledge store where agents and humans collaborate on structured data. Think:

  • Personal knowledge bases — daily logs, notes, and dossiers in markdown with rich frontmatter
  • Task trackers — markdown files where status: complete or [snoozed:: 2026-05-10] are real, queryable data
  • People/CRM directories — a folder of markdown files, one per person, with structured metadata and append-only interaction logs
  • Config-as-data repos — YAML and JSON files that represent system state, not just system configuration
  • Wiki-style collaboration — multiple agents and humans editing overlapping files, always committing, always rolling forward

In these repos, commits aren't milestones—they're the transaction log. Every small mutation should be its own commit, because git history is the audit trail. The filesystem conventions (frontmatter fields, inline tags like [due:: 2026-03-01], section headers as stable anchors) form a lightweight schema that agents navigate constantly.

etch is the primitive for this pattern. It lets an agent say "set this field" or "append to this list" in a way that's precise, auditable, and committed—without falling through to the full generality (and full risk) of shell access or patch construction.
